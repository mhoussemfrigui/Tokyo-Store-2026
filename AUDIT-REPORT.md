# SYNTHESIS

## Executive summary
Overall the Tokyo Store codebase is structurally sound and mature: the data model, server-action/workflow layering, and authoritative re-resolution patterns (order tax, shipping, promotions) are mostly correct, and the great majority of the 78 verified findings are low/info-severity polish rather than broken core flows. However, the audit confirms two systemic weaknesses that map directly to the concerns you raised. First, a large, recurring class of "write-only / dead settings": admin controls that are collected, validated, and persisted but that NO storefront, invoice, or SEO surface ever reads. This spans nearly every domain — root-category SEO meta, sub-category attribute filters, brand/category descriptions, the order-number prefix, CMS page-builder hero image + CTAs + style/alignment/caption fields, the "checkout" banner placement, nav "open in new tab" and sub-items, site WhatsApp/hours/legal-name/tax-id, the help-page contact.*/showroom.* block (reading keys NO panel writes), coin badge colour, promotion description, and the media-settings stub the sidebar links to. Operators routinely fill these in and see nothing happen, and several helper texts actively lie about where the data appears. Second, a naming/label-vs-function class: tabs, labels, and icons whose name does not match behaviour — the loyalty program shown as both "GZ Coins" and "GZ Stage", the "Paiement (clés API)" sidebar entry that now also owns COD/express routing, the CreditCard icon on a page that no longer configures payment, the attribute "Choix unique (radio)" type that always renders checkboxes, the System tile claiming /checkout still configures payment/email, and several "pts" vs "coins" and decimal/step inconsistencies. Layered on top are a small number of genuinely serious correctness/integrity bugs that deserve priority regardless of the theme: editing any product silently wipes its per-product VAT override (wrong tax charged at checkout), the default quick-buy/email-off checkout fails for guests because the server hard-requires email/city that the runtime config defaults OFF, adding a default address violates a DB unique index, code/URL coupons scoped to product/category silently grant zero discount while burning a redemption, every audit event is written twice, and raw customer emails are stored unredacted in the audit log. The codebase is not in a fragile state, but the settings-to-frontend wiring and admin labelling need a deliberate sweep.

## Cross-cutting themes

### Write-only / orphan admin settings — saved but never read by any frontend, invoice, or SEO surface
The single largest recurring pattern. An admin field is rendered, validated, and persisted through the workflow, but no consumer ever reads the value back. Operators enter data expecting an effect and get none; in several cases helper text falsely promises where it appears. This is the core of your 'dead settings' concern and recurs in essentially every domain.
Domains: Catalog — Categories/Brands/Attributes, Catalog — Products, CMS — Pages/Banners/Navigation/Showcase/Settings, Orders/Checkout, Site Settings / SEO, Marketing — Promotions/Coins/Newsletter, Media/Import, Customers/Account
Examples: src/app/(shop)/[slug]/page.tsx:168-177 (root category meta_title/meta_description saved, never used); src/app/(shop)/[slug]/[sub]/page.tsx:104-112 (sub-category attribute filters saved, never rendered); src/components/admin/category-form.tsx:253-259 (category description + false 'admin/panier' helper); src/components/legal-page-renderer.tsx:81-151 (CMS hero image+CTAs, CTA style/bg, stats layout/caption, text alignment all ignored); src/lib/api/cms.ts:188-197 (nav open_in_new_tab and sub-items dropped); src/workflows/order/place-order.ts:100-104 (order number_prefix hardcoded GZ-); src/app/admin/marketing/coins/coins-panel.tsx:116 (coin badge_color never rendered)

### Orphan reads and false helper text — UI promises that don't match where data flows
The inverse and a compounding aggravator of the orphan-settings theme: storefront code reads settings keys that NO admin panel ever writes (so the section is permanently empty), and admin helper/description strings claim a value surfaces on pages where it never does. These actively mislead operators and generate support tickets.
Domains: Site Settings / SEO, CMS — Settings, Catalog — Categories
Examples: src/app/(shop)/help/page.tsx:44-72 (reads contact.*/showroom.* that no panel writes — contact block always empty); src/app/(shop)/help/page.tsx:27-28 (comment falsely says settings admin writes contact.*/showroom.*); src/app/admin/cms/settings/settings-panel.tsx:96 ('Contact' section claims help-page+footer; appears on neither); src/components/admin/category-form.tsx:255 (helper 'Visible dans admin, panier' — false)

### Label / icon / name does not match function (naming mismatch)
Tabs, sidebar labels, icons, and admin option labels whose displayed name implies behaviour that the underlying code does not deliver. This is your second stated concern. Ranges from a customer-facing dual-brand bug to cosmetic icon mismatches.
Domains: Marketing — Coins, System — Payments, CART/CHECKOUT, Catalog — Attributes, Customers
Examples: src/app/(shop)/account/account-client.tsx:119 vs 219 ('GZ Stage' vs 'GZ Coins' for the same program, same component); src/app/admin/_components/admin-shell.tsx:129 ('Paiement (clés API)' now also owns COD + express routing); src/app/admin/_components/admin-shell.tsx:132 (CreditCard icon on a page that no longer configures payment); src/app/admin/system/page.tsx:27-33 (System tile claims /checkout configures payment/email/bank-refs); src/app/admin/catalog/attributes/[id]/attribute-detail-panel.tsx:78 ('Choix unique (radio)' always renders checkboxes); src/app/admin/customers/page.tsx:128 ('pts' vs 'coins'/'GZ Coins' elsewhere)

### Root vs sub-category storefront divergence — features wired on the parent page only
The sub-category page (where most products actually live, on leaf categories) renders the SAME CategoryPageClient as the root page but omits whole blocks of admin-configured data that the root page passes, so they silently fall back to empty defaults. A repeated 'same component, different wiring' shape that turns several admin settings into orphans specifically on the highest-product-density pages.
Domains: Catalog — Categories
Examples: src/app/(shop)/[slug]/[sub]/page.tsx:104-112 (omits filterAttributes/productValueIds, breadcrumb, siblings, trustLabels, gridBanners); src/app/(shop)/[slug]/page.tsx:493-534,599-612 (root passes all of them); src/app/(shop)/[slug]/category-client.tsx:213-222 (props fall back to []/{}/empty)

### Money/tax precision and unit inconsistencies (millimes vs centimes vs whole dinars)
The money scale is millimes (MINOR_PER_DINAR=1000, 3 decimals) but several input steps, formatters, and recompute paths assume whole dinars or 2 decimals, or treat a per-product/per-line tax override as fragile. Mostly display/UX, but tax-override loss (priority #1) and the invoice recompute divergence have real financial blast radius.
Domains: Catalog — Products, Orders/Invoice, INFRA — Formatting, CART/CHECKOUT
Examples: src/components/admin/product-variants-editor.tsx:316-324 (variant price input no step → integer dinars only); src/app/admin/orders/[id]/partial-refund-form.tsx:77 (step 0.01 vs millime 0.001); src/lib/price.ts:100-122 (formatPrice ignores price.decimals; formatMoneyWithCurrency defaults 2dp on TND); src/lib/actions/order.ts:188-204 (invoice 'recalculer global' drops per-line rates + shipping tax)

### Server schema vs runtime-config contract mismatch in checkout (validation requires what the UI hides)
The order schemas unconditionally require fields (contactEmail .email(), city .min(1)) that the quick-buy runtime config defaults to disabled/hidden, and in one case the admin panel's default-checked rendering disagrees with the runtime default-false. Net effect: the marketed default 1-tap flow fails for guests with a generic 'Validation échouée'. A specific, high-impact shape of admin↔runtime disconnect.
Domains: CART/CHECKOUT, Orders
Examples: src/workflows/order/place-quick-order.ts:31,37 (contactEmail/city hard-required); src/lib/checkout/quick-buy-config.ts:161-174 (email/city default OFF at runtime); src/app/admin/system/checkout/checkout-settings-panel.tsx:173 (panel default-checks email while runtime defaults false)

### Half-implemented / dead feature surfaces (column or branch exists, no end-to-end path)
Schema columns, function parameters, enum members, and code branches that are partially wired — written-but-never-read, read-but-never-written, or reachable from neither UI nor production callers. Low individual impact but a broad maintenance-and-confusion tax, and one (uploadByUrl) ships an un-SSRF-hardened fetch.
Domains: Catalog — Products/Reviews, Orders, Media/Import/Data, Customers, CMS, System, Marketing
Examples: src/modules/catalog/review/schema.ts:32 (helpful_count never written/read); src/workflows/catalog/create-category.ts:101,166 (filter_config dead write branch); src/workflows/data/_image-uploader.ts:96-141 (uploadByUrl never called, bare fetch, no SSRF guard); src/lib/actions/customer.ts:52 (setAsDefaultBilling never sent by storefront); src/modules/import/schema.ts:108 (import_jobs.kind default-only, never read); src/modules/order/schema.ts:44 (card_stripe enum, no provider/UI)

### Stale comments / documentation that misdirect maintainers
Doc-comments and schema comments describing behaviour that no longer exists, pointing to the wrong file, or contradicting an actual DB constraint. No runtime effect individually, but the customer/schema.ts default-address comment arguably caused the address ordering bug (priority #5), showing this theme can incubate real defects.
Domains: Catalog — Products, Customers, CMS, SYSTEM — Audit
Examples: src/modules/customer/schema.ts:25-27 (claims NO DB default constraint; two partial unique indexes exist); src/types/catalog.ts:113-115 (video title 'falls back to <name> en action' — no longer true); src/lib/wishlist/session.ts:11 (merge 'see signin workflow' — actually in getWishlistSlugsAction); docs/modules.md:83 (describes a single audit subscriber; two exist → double-write)

### Audit-log integrity and PII exposure
The audit subsystem has two correctness/security defects that compound: every allowlisted event is written twice (curated + wildcard subscribers both fire, no unique constraint), and both subscribers store the raw event payload — including plaintext customer emails — unredacted, then render it verbatim in the admin UI, despite the structured logger deliberately redacting the same payload. Cron-driven purges also leave no audit trail while manual ones do.
Domains: SYSTEM — Audit/Search/Tracking
Examples: src/events/subscribers/audit-everything.ts:45 (raw payload, fires for every event); src/events/subscribers/audit-trail.ts:178 (curated path also raw + duplicate row); src/lib/telemetry/redact.ts:39-46 (redactor exists; audit path bypasses it); src/app/api/cron/retention/route.ts:81-106 (scheduled purge emits no audit event)
