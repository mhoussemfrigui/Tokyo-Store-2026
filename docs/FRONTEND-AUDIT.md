# Tokyo Store — Front-end Audit

_Read-only audit of every storefront surface (10 groups, 81 findings: 4 high · 29 medium · 48 low)._

## Group summaries

- **Shared chrome + systemic spacing** — Chrome (header/footer/mobile-nav/layout) is well-built and the Tokyo focus/select system is compliant (no raw selects, crimson --ring); the real issues are a systemic footer-gap inconsistency (main's blanket pb stacks on the full-page views' own paddingBottom), a few full-page views bypassing the .tokyo token flow with nested .tokyo + min-h-screen + inline hex, and backend-truth gaps in the chrome (hardcoded social follower counts and a hardcoded header phone).
- **Shared content-page component (legal/info routes: cgv, cgu, privacy, cookies, mentions-legales, carrieres, garantie-retours, help, nos-boutiques, notre-histoire, service-client)** — Layout and responsiveness of the shared ContentPage are clean (no raw selects, 44px targets, breadcrumb handles mobile); the real problems are backend wiring — all 11 pages are hardcoded TS that completely bypass the repo's existing CMS pages system — plus a few spacing/readability inconsistencies in the component.
- **HOME page (src/app/(shop)/(tokyo)/page.tsx)** — Responsive/structure/footer-spacing/dropdown/a11y are clean and carefully built (consistent rhythm tokens, correct mobile-nav clearance, no raw selects, descriptive hero alt); the real issues are all backend-truth: the entire home is hardcoded in component source while a home.blocks backend exists, plus fabricated store cards, a fake countdown, mis-wired editorial tiles, and placeholder tel: CTAs.
- **Category + Search listings (/[slug], /recherche)** — Well-structured shared Normal V1 listing system wired to real backend products; no raw <select> (sort is a compliant Tokyo custom listbox, mobile filter Sheet correctly re-scopes its portal, footer handles floating-nav clearance). Findings are medium/low: search autocomplete preview + "trending" list not backed by the real search backend, hardcoded phone numbers, an ARIA listbox misuse, and minor radius/spacing inconsistencies.
- **Product Detail Page (PDP)** — The PDP is well-structured, backend-wired and responsive overall, and both dropdowns already use the Tokyo SelectField (no raw <select> — the task's premise is stale); the real problems are a high-impact express-order bug that drops the selected variant, and the always-on mobile/tablet buy bar overlapping / over-padding the footer.
- **purchase-path** — Purchase path (/panier, /checkout) is largely solid: dropdowns are compliant SelectFields, order/address/pickup/shipping/Tokyo Care are genuinely backend-wired, no dead links or TODOs. Main issues: bottom-padding stacks on the layout's main pb (inconsistent 40/56/96px gaps before footer), a redundant min-h-screen/.tokyo/bg wrapper, a hardcoded support phone and a promotions-blind total (backend-truth), plus minor a11y gaps.
- **ACCOUNT + FAVORITES** — Both /account and /favoris are solidly backend-wired (orders/profile/addresses via server actions, favorites+cart via the backend wishlist store, SSR recommendations) with the compliant SelectField and no dead links or double footer padding; findings are a handful of mobile responsive/overlap issues (tight CTA, sticky/floating elements colliding with the fixed header and floating nav) plus minor structure/a11y nits — no high-severity defects.
- **reels** — Well-built, mostly clean Tokyo-compliant page (no raw &lt;select&gt;, shoppable products are REAL catalogue data, sort menu is Tokyo-styled); main issues are a footer-spacing padding stack, raw category slugs shown as user-facing text, dead href="#" social links, and acknowledged demo video/social metrics.
- **AUTH pages** — Auth surface is well-structured, fully backend-wired, dropdown-free, and overflow-free; footer is correctly pinned to the bottom on these short pages. Only three low-severity polish items (duplicated bottom padding, field errors not programmatically linked, one short checkbox tap target).
- **Utility pages — /rendez-vous, /suivi-de-commande, /p/[id]** — Three utility surfaces are mostly clean and real-backend-wired, but the rendez-vous flow silently breaks when more than one appointment location exists (no location-picker step), two views duplicate bottom padding (pb-8 vs the store's pb-4 convention), the track page hardcodes the service phone, and the legacy /p redirect is a temporary 307 instead of the 308 its siblings use.

## Findings by category


### FOOTER-SPACING (11)

- **[HIGH]** `src/storefront/components/storefront/product-view.tsx:1090` — /[slug] (product)
  - **Issue:** The always-on mobile/tablet floating buy bar (fixed inset-x-0 bottom-0, lg:hidden, ~130px tall: img h-11 + gap + row2 h-[52px] + pt-3 + safe-area pb) overlaps the footer. The footer only reserves pb-(--dock-bottom) ≈ 80px on phones and md:pb-[calc(1rem+safe)] ≈ 16px on tablet (footer.tsx:201). The data-buy-bar="shown" swap (globals.css:1558) only slides the ~76px bottom-nav away and bumps scroll-padding — it adds no layout padding. So at the document bottom the ~130px bar covers the footer's bottom legal/copyright strip; it is WORST at tablet widths 768-1023px, where the footer reserve collapses to ~16px while the bar still shows (lg:hidden), overlapping ~110px of the footer.
  - **Fix:** When data-buy-bar="shown", add real bottom clearance equal to the bar height (~8.5rem incl. env(safe-area-inset-bottom)) below <lg. e.g. globals.css: html:has([data-buy-bar="shown"]) footer.envelope-x { padding-bottom: calc(env(safe-area-inset-bottom) + 8.5rem); } scoped to @media (width < 64rem), so the bar never covers the footer on phone or tablet.
- **[MEDIUM]** `src/app/(shop)/(tokyo)/layout.tsx:59` — systemic — all routes; most visible on product PDP (/p/[id], [slug]), /panier, /checkout
  - **Issue:** The gap before the footer is produced two different ways, so it is inconsistent across routes. <main> applies a blanket pb-14 sm:pb-16 lg:pb-20 (56/64/80px) to EVERY page. Token-flow pages (content-page, account-view, category-view, search-view, favorites-view, reels-view, home) rely on that alone, so their content→footer gap is ~56px on mobile. But the full-page views ADD their own bottom padding that STACKS on top: product-view.tsx:344 (pb-[164px] lg:pb-10), checkout-view.tsx:372 (inline paddingBottom 96/40), :342 (pb-14), :317 (pb-10), and cart-view.tsx:71 (inline paddingBottom 96/40). Net result: mobile PDP shows ~164+56=220px of empty beige before the footer, cart/checkout ~96+56=152px, vs ~56px elsewhere — a 3–4× difference in the same beige canvas.
  - **Fix:** Single-source the bottom gap. Either make <main> pb-0 and give the token-flow views an explicit footer gap (e.g. a shared rhythm token), or have the fixed-bar views (product/cart/checkout) set their clearance to (bar height − main's pb) instead of bar height, so the view pb and main pb don't double up. Pick one mechanism for the content→footer gap store-wide.
