# Tokyo Store — Website Section Map

> Index for detailed section-by-section checkups. Storefront lives under
> `src/app/(shop)/`; admin under `src/app/admin/`; business logic in
> `src/modules/<name>/`; mutations in `src/workflows/` (registered via
> `src/workflows/index.ts`) called through server actions in `src/lib/actions/`.
> Read-side helpers live in `src/lib/api/*` and module `queries.ts`. Settings
> live in the `site_settings` k/v table (read via `cms/setting`) plus dedicated
> tables (`payment_provider_settings`, `oauth_provider_settings`, `tax_rules`,
> `delivery_agents`, `pickup_locations`, …).
>
> _Generated as a navigation aid; verify against the live tree before relying on
> any single path — routes evolve. Last reviewed against code: 2026-10-04._

**Adding a route.** Any new first-level route directory (`src/app/<name>` or `src/app/(group)/<name>`) must be added to `src/lib/pages/reserved-routes.ts` (`STATIC_SINGLE_SEGMENT_ROUTES` if it serves `/<name>` itself), and a new multi-segment file route that does not call `resolveRedirect` must be listed in `APP_ROUTE_SHAPES`; `src/lib/db/tests/reserved-routes.test.ts` enforces both.

**Mega-menu (composable).** `SiteHeader` is fully DATA-DRIVEN: `getComposedNavRoots` (`lib/api/nav-composer.ts`) resolves the roots from the materialized `main` menu (`nav_items` + per-root `config` JSONB, migr 0180) + the live catalog/média, falling back to the 3 default roots when un-seeded. Each root's dropdown is composed as an explicit list of **columns** (1–4, left→right), and each column holds its own ordered **blocks** — `links` (free links), `categories` / `brands` (titres | logos | les deux) / `products` (aperçu) / `image` (média + **format** paysage/carré/portrait/long/très-long with per-format recommended dimensions + lien + visible-mobile). An image is ALWAYS a sole-image column — `parseNavDropdown` splits any image out of a shared column (the desktop panel only paints an image alone in its column), so an operator who drops an image beside content still sees it and old mixed configs self-heal. An image column renders position-aware: a flush featured panel at an EDGE, a contained rounded card in the MIDDLE, at the chosen fixed aspect (never stretched/cropped by menu length). A list block can set a **max-par-colonne** cap that wraps its items into column-major sub-columns (overflow). Per-root mobile visibility, all edited in **CMS → Nav Menu** (the `NavBuilder` composer → `saveHeaderNavAction`, replace-all). The 3 default roots (Boutique=categories, Marques=brands, Maison=links) are materialized once at boot by `ensureHeaderNavRoots`, which migrates each former `nav_*` featured banner into an image block (imagery now lives in `nav_items.config`, not the `nav_*` banner placements — those are legacy). A root whose only dynamic block resolves empty (e.g. Marques with no active brands) is omitted (hide-when-empty). Custom internal-ref links whose category / brand target is deactivated are pruned (liveness); manual-URL links are kept.

### External / headless API (`src/app/api/**`)

First-class integration surface (not a storefront route), governed by
`/admin/system/api` above. Key-required BY DEFAULT (`Authorization: Bearer …` /
`X-API-Key`, scoped `<resource>:read|write`); reads can be opted public per
route. Single gate: `enforceExternalApi` (`src/lib/api-auth/enforce.ts`);
catalog/scopes/public-toggle source of truth: `src/lib/api-auth/route-catalog.ts`
(`EXTERNAL_API_ROUTES`). Writes run the SAME workflows the dashboard uses (actor
= the key's owner). **Full reference: `modules.md` §7.1.**

## 4. Watch list (likely drift)

- **Subscriber registration** — `lib/auth/server.ts` AND `instrumentation.ts` both pull in `@/events/subscribers`; `registerAllSubscribers` is idempotent via a `globalThis.__gz_subscribers_registered` flag — keep it that way (no double side-effects).- **Brand routing duality** — flat `/[slug]` resolves brands while `/brand/[slug]` permanently redirects; the polymorphic `/[slug]` resolver (category/product/brand) is the highest-collision surface — slug clashes are a real risk.
- **Checkout settings spread** — `checkout.*` keys are read across `lib/checkout/{copy,delivery,shipping,quick-buy-config}.ts`, `product-tabs.tsx`, `order/[id]/page.tsx`, and `place-order.ts`; a key written by `/admin/system/checkout` or `/payments` but not read (or read in only one place) is the most likely written-but-unread candidate.
- **Shared payment config (cart == express)** — `checkout.quick.cod_*` + `checkout.payment.*` (Paiement page) are the SINGLE allowed-methods set for BOTH the cart and the express flow; `resolvePaymentMethod` (`quick-buy-config.ts`) is the one authoritative gate and the customer always chooses COD vs online. There is no express-only routing key any more (the old `force_online`/`default_method` were removed — they let the cart silently coerce a COD pick to online).
- **Settings vs dedicated-table duplication** — payments and OAuth keep both `checkout.payment.*` / `auth.social.*` k/v flags AND `payment_provider_settings` / `oauth_provider_settings` rows; the k/v flag and the table row must not contradict (enabled in one, configured-off in the other). For OAuth the flag is authoritative: `auth.social.<provider>_enabled` off unregisters the provider from Better Auth (`buildSocialProviders`), and a provider is live only when it is enabled AND its credentials resolve (env wins over the stored ciphertext).
- **Full settings-map → client leak** — admin pages must pass only the narrowed `<prefix>.*` slice of `getSettingsMap()` to client panels (the full map carries other panels' `*_enc` secrets) — `pickSettings(map, prefixes)` in `src/lib/settings/pick-settings.ts`. Settings pages must also fail closed: no `.catch` → defaults on the read, or a save would persist the defaults over live config. Audit any new settings panel for both.
